## Connection-budget correction

Frozen §3.4 says one Backup connection total, no concurrent Staging backup, with Web/Worker/Scheduler pools totalling 13, then Backup 1 = 14 (or its conservative table total 15 including a Migration). The current exported-snapshot implementation really uses **two simultaneous connections**: a read-only `psql` exporter/inventory session plus one `pg_dump --snapshot` session. The preliminary server-version query finishes first. File copy prolongs the exporter transaction, which can retain MVCC versions and delay vacuum cleanup; measure that duration and database growth. Restic upload/verification occurs after COMMIT and requires no PostgreSQL connection. [PostgreSQL synchronized snapshots](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION), [pg_dump snapshot option](https://www.postgresql.org/docs/18/app-pgdump.html).

**Recommended explicit disposition:** approve two simultaneous connections for the weekly command, charged as **Scheduler slot 1 + Backup reserve 1**, with the existing matching scheduler single-job boundary excluding other scheduler database jobs. This keeps the conservative combined total at 14: remaining application allocations 12 + weekly 2. Do not hide the two sessions behind the old wording “Backup 1 total.” Daily/pre-deploy dumps still use one active connection. Migration remains serial with backup under the existing deployment rule; no new old/new Web-pool overlap is allowed.

Move backup-lock acquisition before the initial database-version probe so rejected overlap does not briefly open an extra DB connection. For an approved one-shot, the matching ordinary scheduler must already be stopped/paused under the existing host operating boundary; a separate container's `/tmp` lock does not enforce that exclusion. Staging backup is on demand only while Production scheduling/backups are paused under the existing protected Staging procedure. Current environment-private `flock` files do not enforce a cross-environment limit. These are concrete operating preconditions to validate, not permission to add a shared lock service, bypass FD9 or launch parallel backups.

If the existing scheduler exclusion cannot be guaranteed, the truthful upper-bound table becomes 15 with weekly backup (16 in the table's hypothetical Migration overlap), leaving 15/14 out of 30; approval of that alternative cannot be inferred from spare connections. The recommendation is to reuse the idle slot and preserve Migration exclusion, not raise `max_connections` or add pooling infrastructure.

Alternatives are less proportionate: a live dump followed by an unrelated SQL inventory loses snapshot consistency; restoring to a scratch database solely to derive the inventory adds database/storage/privilege work; parsing SQL COPY output introduces a parallel database-decoding path. A quiesced one-connection design requires stop/resume ownership across Web/Worker/Scheduler and a longer maintenance window. No such alternative is implemented here.

## Routine verification versus acceptance rehearsal

Current Candidate code performs `restic check --read-data`, then **file-restores every selected snapshot** before retention, runs set/checksum/dump-payload verification, and deletes each scratch copy. With four retained snapshots, a normal fifth admission downloads the whole repository plus five sets. These are file restores, not five PostgreSQL restore transactions. `restore --verify` and the existing checksum helper reread local bytes as well. `prune --max-unused 0` can additionally download/re-upload partially used packs. Restic explicitly documents the full-read bandwidth cost and prune repacking tradeoff. [Repository checks](https://restic.readthedocs.io/en/stable/045_working_with_repos.html#checking-integrity-and-consistency), [Restic pruning](https://restic.readthedocs.io/en/stable/060_forget.html#customize-pruning).

Propose the following replacement, subject to the Owner's disposition rather than editing execution now:

1. **Every new weekly backup:** retain local seal/hash/full dump-payload checks; upload the set; restore **that new exact snapshot once** with `--verify`; run `verify-backup-set` on its bytes. This verifies new recovery data rather than re-proving an unchanged retention implementation. Failed upload, missing contents, checksum or dump failure blocks admission and all retention.
2. **Routine retention (recommended):** keep **one** `restic check --read-data` pass over repository packs before deletion; inspect each candidate's existing completion/set/checksum metadata and Restic file listing for schema/environment/required-file closure. The full pack pass verifies stored content, while the existing source manifests describe the previously validated dump/original set. Do not file-restore every unchanged older snapshot again. A missing pack or byte-corrupt repository aborts retention; missing/unknown/incomplete set metadata does not count. Remove only oldest excess eligible snapshots after the new exact snapshot has passed its full read-back. Do not replace this with a bare `forget --keep-last 4`, which could count an incomplete snapshot. No new ledger, table or verification-tag state machine is needed.
3. **Acceptance rehearsal:** actual PostgreSQL restore and application/rights/variant verification belong in the existing empty-environment acceptance exercise before launch, repeated for material backup/restore/schema/recipe changes or a recovery incident. They are not required for every old snapshot in routine retention. The one full repository pack pass above is an operational byte-corruption check against the actual retained data, not a repeated application restore to re-prove retention logic. Moving that pass to a less frequent scrub would reduce bandwidth further but leave old-pack latent corruption undetected between scrubs; ordinary `restic check` verifies structure, not old pack bytes. That weaker routine policy is an explicit alternative for the Owner, not the recommended implicit simplification or a new scheduled job here.
4. Replace forced zero-unused repacking with standard `restic prune` behavior after eligible forget, followed by structural `restic check`; default 5% unused allowance reduces compulsory repacking while maintaining four snapshot references. This trades some remote unused-pack storage for less work/traffic; measure the normal result. Do not introduce an indefinite second local replica or silently count failed prune as failed DB backup. Prune failure is a separate observable maintenance failure; retained valid snapshots are preserved.

Required controls: complete-set consistency, private separation, checksum/dump integrity, new-snapshot read-back before deletion, last-valid preservation and independent failure visibility. Risk-proportional controls: kernel overlap refusal and exact environment/repository/mount selection. Optional hardening, not scheduled here: extra historical-data scrubs between weekly runs or an outbound hostname allowlist beyond the already approved endpoint/client policies. No new proof platform, queue, Worker or lifecycle wrapper is proposed.

### Quantified cost model (not measured target-host data)

Let `S_i` be each logical complete-set size, `B_i` its downloaded encoded chunks, `R` all repository pack bytes, `D` a daily dump, `C` metadata/cache space and `E` retained deployment extras. Current downloads before prune are approximately `R + sum(B_i)` for up to five snapshots; the recommended routine path is approximately `R + B_new + metadata`, eliminating four older file restores. A separately approved less-frequent-scrub policy could reduce nonscrub runs to `B_new + metadata`, with the detection tradeoff above. Deduplication/compression/cache and Provider billing can change exact bytes, so these are planning estimates.

For illustration only, if each set downloads 10 GiB and unique repository packs occupy 12 GiB, the current fifth-admission check reads about 62 GiB; the recommended path about 22 GiB plus metadata (about 65% less). Moving the full pack pass off routine runs could lower those runs to about 10 GiB (about 84% less), but is not assumed. Prune adds variable download/upload traffic. No COS price, formal dataset size or RPO/RTO is assumed.

Local **peak space is not reduced merely by removing the old-restore loop**, because it was sequential: both designs need roughly `S_new + max(S_readback) + C`, plus `7D + E` for retained DB backups and all existing live database/media/OS/log/image usage. At a 10 GiB logical set that is about 20 GiB transient space before the other allocations. Local scratch writes fall from roughly five sets to one. A protected remote repository does not place `R` on the local disk. Check the unchanged 60 GB budget before activation; no automatic disk/RAM/vCPU increase or O-18 narrowing follows from these estimates.

## Draft ADR — Environment-scoped Provider egress and bounded backup verification

**Status:** Proposed; coordinator must obtain explicit Owner disposition before implementation. Reason: declared internal-only application topology cannot execute existing Provider paths; S6-06 also has a two-session allocation and excessive historical read-back cost that must be made explicit.

**Decision proposed:** adopt topology A with only the five current callers attached; keep Production AI dormant, database/cache internal, per-environment secrets private and COS backup-only. Approve weekly exporter + dump as Scheduler 1 + Backup 1 under the existing single-job/one-shot pause rules. Verify each new remote set once before retention, replace historical file-restore repetition with one repository byte-integrity pass plus structural/manifest checks, and use standard prune behavior. A weaker less-frequent byte-scrub policy would need separate explicit disposition.

**Consequences and tradeoffs:** two small standard network declarations solve the whole current call chain without a new service; general outbound capability increases and must preserve cross-environment denial. Idle connection reuse avoids a capacity increase but depends on real scheduler exclusion. Routine traffic falls; the recommended single repository pass still detects old-pack byte corruption before retention. The lower-traffic alternative would detect that corruption only at its selected scrub/restore, not by structural checks alone. Each successful new admission still supplies a currently verified recovery set before any deletion. Standard prune may retain up to its default unused-data allowance instead of forcing zero unused bytes.

**Compatibility and rollback:** no Schema/Migration or public URL/Redirect change; retain existing set-v1 read compatibility and all source backups. Roll back the matched network/config/scripts as described above, with Provider work unavailable and protected activation stopped if necessary. No alternate online storage, phase advancement or external operation is authorized.

**Owner disposition to record:** A versus B/C; explicit Scheduler-slot reuse for weekly two-session backup; recommended new-set read-back + one weekly repository integrity pass + metadata retention/default-prune policy (or an explicitly weaker scrub cadence with its stated tradeoff). These choices are presented by the coordinator, not independently requested from the Owner by this Developer task.
