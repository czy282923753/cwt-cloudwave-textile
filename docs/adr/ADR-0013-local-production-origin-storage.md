# ADR-0013: Local Production Origin Storage

Status: **Accepted by the project owner for Phase 1B Stage 0 on 2026-08-05. Implementation is not authorized by this ADR.**

## Context

Phase 1A implemented isolated Public, Private, and Import storage contexts, controlled public/private media routes, Asset eligibility, scan/processing/rights checks, and provider adapters. Its current Production startup policy requires an S3-compatible online provider. The Phase 1B frozen deployment decision instead places initial online media on the single Tencent Singapore host and uses a private COS bucket for off-site backup only.

The provider choice changed, but the Asset, relationship, authorization, revocation, and URL boundaries did not. On a 60 GB single host, local paths also need explicit environment/partition isolation, disk safeguards, backup, and future data-disk compatibility.

## Decision

Initial Production and Staging media origins are hardened local host volumes at the exact paths approved in [Phase 1B Owner Decisions](../PHASE_1B_OWNER_DECISIONS.md#1-local-production-and-staging-absolute-roots).

The existing `assets.id` remains the media identity. Public HTML uses only the existing application-controlled route contract:

```text
/api/public-assets/{asset-id}/
```

The public route resolves the Asset through the configured environment/partition adapter and rechecks storage context, scan, processing, deletion, rights, approved live relationship, and public entity eligibility on delivery. Filesystem paths, mount names, filenames, hashes, Object Keys, backup locations, and COS URLs are not public contracts.

Private Inquiry delivery remains record-scoped and separate. Import files remain internal until existing scan/Finalize and an authorized Asset relationship make an approved original eligible. Reverse proxy and static servers must not serve `/srv/cwt` or `/etc/cwt` directly.

Exactly one configured origin provider is authoritative for an Asset storage context in an environment. The existing S3-compatible adapter remains a future migration target, not a simultaneous second live relationship or public URL authority.

## Alternatives

1. **Use S3/COS as online origin immediately.** Technically compatible, but rejected for the approved initial topology and operating scope. COS remains backup-only until a later authorized migration.
2. **Serve `/srv/cwt/...` directly through the reverse proxy.** Simpler byte delivery but bypasses revocation, rights, revision, private/public, and eligibility checks.
3. **One shared media root for Production and Staging.** Lower directory count but violates environment isolation and creates cross-environment data exposure.
4. **Store media inside the application image or repository.** Breaks immutability, persistence, backup, capacity, and Secret/data boundaries.
5. **Require a new media table for local files.** Unnecessary because Asset and storage metadata already own identity and lifecycle.

## Schema / Migration impact

No business Schema change is required for the provider decision. Existing Asset IDs, storage context, provider/object metadata, variants, relations, Finalize Manifest, Recovery, and Cleanup remain authoritative.

No Migration is generated by this ADR. Stage 6 implementation may change environment validation and deployment artifacts only. If later evidence requires a storage metadata change, it must use a separately reviewed forward Migration; `0000`–`0017` remain immutable.

## URL / SEO impact

No public media URL, Product/Content route, Canonical, Redirect, Sitemap, or Index rule changes. Stable Asset-ID routes allow later relocation to a data disk or object storage without rewriting public HTML.

Initial Cloudflare behavior must not make correctness depend on controlled-media caching. Cache expansion requires separate versioned URL/revocation/cache-invalidation acceptance.

## Security / privacy impact

- Production/Staging and Public/Private/Import roots are absolute, nonoverlapping, least-privilege, and not web roots.
- Private Inquiry files never enter Public or Import roots automatically.
- Application delivery never trusts a caller-supplied path or raw Object Key.
- Traversal, symlink escape, mount mismatch, permission, streamed-byte, signature, decode, scan, rights, deletion, and relationship checks remain fail closed.
- Backup archives containing private media are encrypted and access-controlled.
- Logs and errors do not disclose absolute paths, keys, private filenames, or customer data.
- Disk thresholds and bounded image/import work must prevent local storage exhaustion from corrupting business operations or reporting false success.

## Compatibility

The application-controlled route and Asset ID remain compatible with existing public records. Provider selection occurs behind the existing storage adapter boundary.

The current S3-only Production startup gate is intentionally incompatible with the approved deployment and must be replaced, not layered with a bypass flag. Local Production startup must fail closed unless every required absolute root, ownership/mode, isolation, writable/readable probe, disk threshold, and backup/readiness condition passes.

Future object-storage migration copies verified bytes and changes provider metadata through one governed migration/cutover. It does not create new Asset IDs or public URLs merely because storage moved.

## Rollout

1. Stage 6 reviews exact mount ownership/modes, disk budget, backup inclusion, and environment isolation.
2. Deployment validation creates/probes the approved roots without exposing them publicly.
3. Synthetic Assets validate Upload, Finalize, derivative, controlled public delivery, private record scope, revocation, Recovery, Cleanup, and restart behavior.
4. Staging proves cross-environment denial, 70/80% disk controls, backup/restore, and future mount relocation.
5. Production configuration and formal media remain separately authorized Stage 7/8 actions.

No step in this ADR authorizes creating directories on a real host or configuring COS.

## Rollback

Before formal cutover, disable the local-provider feature and retain the Phase 1A configuration. After bytes are written, rollback uses a checksum-verified snapshot/backup and a previously compatible application image that understands the same Asset-ID route and provider metadata.

Never delete the prior valid originals/provider copy until controlled delivery, relationship eligibility, backup, and full restore pass. If local readiness fails, stop writes and restore the last known valid configuration/data set; do not silently fall back to an unconfigured shared or public directory.

## Rejected duplicate-authority designs

- A second Local Asset table or Local Media Library.
- Direct Nginx/static paths alongside application-controlled Asset delivery.
- Separate Product-import storage/finalize logic outside existing Upload/Finalize/Recovery/Cleanup.
- Simultaneous local and object URLs as equal public contracts.
- Production and Staging sharing a root with path prefixes enforced only by UI.
- A background copier that changes live provider authority without an audited, observable cutover.
