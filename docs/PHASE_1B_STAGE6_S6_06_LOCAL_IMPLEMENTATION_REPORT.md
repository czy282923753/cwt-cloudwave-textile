## Outcome and responsibility boundary

The missing responsibility was an executable recovery boundary: scheduler health could read a completion event, but no standard-tool producer, verification/retention program or safe restore existed; scheduler backup mounts were read-only and the image lacked clients/scripts. `deploy/backup` now owns local dump/set integrity and restoration. Application Domain Services remain the sole public/private/rights/relationship authority.

Daily custom PostgreSQL dumps are fully read through `pg_restore` (catalogue and payload), checksummed, fsynced and atomically finalized. The S6-05 completion event is replaced only after verified durable success. Retention keeps seven valid slots and does not count/delete corrupt or unknown ones. `pre-deploy` creates a fresh extra verified backup before executing the supplied approved command.

Weekly Synthetic recovery uses a PostgreSQL exported snapshot shared by the original-file inventory and `pg_dump`, then copies only bytes matching the database SHA-256 and size. Restic encrypts, checks every referenced repository byte and restores each candidate before retaining four valid sets. Missing/changed source objects and partial sets fail closed. Source manifests are the specified private checksum/completion/path metadata, not a new evidence platform. Original files remain Public/Private-separated; temporary/import/derivative files and runtime secrets are excluded.

`restore-empty` performs an actual transactional PostgreSQL restore only to an empty, unprivileged, Unix-socket-only Synthetic target in a Linux network-none namespace. It refuses protected/nonempty/overlapping roots, wrong identities and networked clients. Verification clears inherited configuration, sets noindex, disabled analytics, a Synthetic mail sink/log transport, fresh auth material and disabled AI; no Web/Worker is started. It compares the restored inventory, calls existing database readiness and public media eligibility, checks original bytes and rebuilds recorded variants using the existing image recipe without rewriting rights, scans, Product evidence or Manifest authority.

## Packaging, mount and complexity changes

The runtime Dockerfile packages PostgreSQL 18.4 clients plus their shared-library closure from the existing pinned Bookworm PostgreSQL image, Restic 0.19.1 with architecture-specific SHA-256, and the backup scripts/non-secret config through the existing per-platform acquisition bundle. Final release construction remains network-none. This does not change any already emitted image.

Scheduler backup mounts are writable; Web/Worker have no backup mounts. Compose validation/tests now enforce both facts. Existing networks, secret grants, CPU/memory limits and O-18 remain unchanged. Cron includes daily backup, the fail-closed weekly entry and the existing work-health probe. No Docker socket or source/Runtime workflow/materializer/validator repair was added. Only the shared Compose mount validator and affected scheduler-count regression were aligned.

No old executable backup logic existed to delete. Shared argument/credential/tool checks and filesystem metadata operations are consolidated rather than duplicated across entry points. The former read-only completion mount is replaced by the same environment-private writable backup bind. No business table, Migration, Worker, Lease, queue or persistent recovery lifecycle is added. An OS `flock` on that bind extends backup overlap refusal to separate approved one-shot containers; its lock is kernel-owned/released on exit, not a database or stale-lock state machine. Existing `/tmp` scheduler locking still covers scheduled non-backup jobs. Complexity increases by the necessary shell programs, private set metadata, standard-tool packaging and a read-only application verification helper; no dual media or restore activation authority is created.
