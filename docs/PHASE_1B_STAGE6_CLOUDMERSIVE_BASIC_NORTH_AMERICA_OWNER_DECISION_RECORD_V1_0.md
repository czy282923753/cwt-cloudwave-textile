## 1. Historical decision

The Owner explicitly approved **Cloudmersive Basic / North America** as the local Stage 6 malware Scanner adapter target.

The Owner acknowledged that:

1. future external use might process private Inquiry files in North America; and
2. Production and Staging required environment-separated API credentials and might require separate subscriptions/accounts.

This decision closed only the then-missing authority to design a local, Provider-disabled Cloudmersive adapter and fake/static validation hooks. It did not assert that an account, contract, key, subscription or external processing path existed.

## 2. Historical non-authority boundary

V1.0 did **not** authorize:

- purchase, spend or acceptance of commercial terms;
- account, subscription or API-key creation;
- DPA, subprocessor, retention, transfer or security-term acceptance;
- credential access, custody, rotation or injection;
- a Cloudmersive/Provider call, test-signature upload or real file transfer;
- use of real Inquiry, customer, Product or Production data;
- protected Staging/Production, DNS, external configuration, Deploy or Push;
- Publish, Index, Production-readiness claims; or
- Stage 7 entry or execution.

Before external use, current commercial terms, DPA, subprocessors, retention, processing region, account/key separation and spend still required separate validation and authorization.

## 3. Historical environment stop boundary

Production and Staging could not share an API key or application Secret. If separate environment credentials required a materially different commercial/account/processing direction, external use had to stop and return to the Owner. No worker could silently reuse one key, change tier/region/Provider, accept terms, create another account/subscription or send bytes to test the arrangement.

The local adapter had to remain disabled without valid environment-specific secret-file configuration and make no Provider call during startup, readiness or local evidence generation.
